# MeshDrop privacy model

Reviewed 2026-10-18 for P8. This describes current local code and its limits. Public deployment/provider policy verification belongs to P9.

## What each component can see

| Component                | Can see                                                                                                                                                               | Retains                                                                                                                                                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser application      | Selected filenames, sizes, bytes, digests, manifests, receipts, peer connection metadata and ephemeral admission/signing credentials                                  | Verified temporary files/checkpoints/source manifests and optional local diagnostics; admission credentials and signing keys stay in memory                                                                                   |
| Worker / room actor      | Room and peer identifiers, presented bearer authority/tickets, origin, admission decisions, forwarded SDP/ICE (which may reveal addresses), request/connection timing | Scoped SHA-256 credential verifiers, room/peer state, epochs, bounded ticket/replay/rate metadata and expiry; no raw capabilities, SDP/ICE, filenames, file manifests, hashes, receipts or file bodies in application storage |
| Approved peer            | Offered labels, sizes, digests and accepted bytes; WebRTC connection information                                                                                      | Received files and local transfer/receipt metadata under that peer's browser policy; exported copies are under their control                                                                                                  |
| TURN relay if configured | Endpoints, timing and volume of encrypted WebRTC traffic                                                                                                              | Depends on relay operation; no relay logging/retention deployment has been verified in P8                                                                                                                                     |
| Host/network provider    | Traffic/request metadata; signaling TLS termination can read signaling content                                                                                        | Provider-managed logs/retention are external to the application and must be configured/reviewed in P9                                                                                                                         |

There is no cloud file-upload/download route, account database, analytics SDK, QR-generation service or camera-frame upload. A direct peer path can expose network addresses to the other peer; diagnostics report only a connection category and selected metrics. Private files are origin-private browser data, not a vault encrypted against a compromised browser profile, operating system or same-origin script.

## Invitations and authorization

Invitations carry a short-lived, single-use bearer in the URL fragment. Fragments are not part of HTTP requests. The app captures an invitation in memory and immediately replaces the visible URL/current history entry with the pathname; pasted/scanned invitations are strictly bounded and origin-validated. The site sends `Referrer-Policy: no-referrer` and makes no analytics calls. QR encoding/decoding and dependencies are served by this origin.

History replacement is not guaranteed erasure of browser data. The production test directly observed Chromium retaining the original fragment in internal `userTypedURL` navigation metadata even when the current history entry URL was clean. Browser history/sync, bookmarks, clipboard managers, extensions, screenshots, a displayed QR, crash/session recovery and someone viewing a device may retain or disclose an invitation. Do not publish invitations or place credentials in query strings; application code cannot undo a query already sent to a server. Expiry, owner approval, single candidate admission, revocation and independent code comparison limit the authority of a leaked invitation, but do not erase external copies.

Owner/peer capabilities travel in Authorization headers. Short one-use socket tickets travel in the WebSocket subprotocol, never query parameters; only the public protocol name is negotiated back. SQLite retains verifiers rather than recoverable bearers. A holder can exercise the corresponding authority until revoked/expired. File/checkpoint hashes alone do not authorize a peer. Reload loses browser room credentials; surviving local files require new admission/comparison before authenticated network recovery.

## Storage, retention and deletion

Default room/invite/ticket lifetimes are 15 minutes / 5 minutes / 30 seconds. Closing or rejecting revokes authority. Alarms clean ticket metadata, expire rooms and purge room/peer/invite/ticket/budget rows after a default one-minute closed tombstone. Runtime/provider scheduling and backups are not a physical-erasure promise. Edge rate keys use a date-scoped hash of the provider-supplied address; raw addresses are not persisted by application code.

Local interrupted/completed transfer data can use 24-hour, seven-day or discard retention. Expiry/purge runs on a later open/check; a closed browser does not run a guaranteed background deletion job. Scoped cancel/clear/delete actions remove the selected browser transfer records and temporary bytes where available. Reopening rehashes bytes before declaring them present or exportable. Eviction, storage clearing and OS suspension can remove data. OPFS and IndexedDB do not prove physical power-loss durability.

Local diagnostics retain at most 10 reports, 512 KiB per report and 4 MiB logical total for up to seven days. Schemas exclude file names, digests, credentials, SDP/ICE/candidates/addresses, raw errors and arbitrary labels. Reports still expose linkable identifiers, byte counts, timing and connection categories. JSON/CSV export is opt-in; no application upload endpoint receives reports. Users can delete local history. Limits exclude database overhead.

Service-worker caching is an exact allowlist of public HTML, hashed code/workers/styles, manifest and icons. API requests, query-bearing URLs, authorization/range requests, foreign origins and file content are excluded. Offline access can revalidate/export surviving local files but does not restore room admission or background transfers. Updates require explicit application.

Downloads, shares, native destinations, copied invitations and exported JSON/CSV live outside browser-store deletion. The user must remove those copies separately. A returned share sheet or started download is not proof that a chosen destination contains a usable copy.

## Logging and evidence

Production application source has no console logging, third-party telemetry, raw request dumping or structured payload logging. User-visible room events use fixed phrases; error boundaries return bounded generic messages and request IDs. Wrangler/workerd development and hosting systems can emit request paths, room IDs, timing and runtime errors. Provider log settings, retention/access, request-header/subprotocol capture and TURN logs require deployment review. Do not enable body/header capture or attach raw signaling to monitoring.

Live test traces, video and automatic failure screenshots are disabled by default. Tests and raw artifacts stay ignored; assertion output, browser internals and third-party tooling can still contain test invitation values and must be reviewed before sharing. Committed evidence uses synthetic content, redacted summaries and reviewed screenshots without invitation QR/capabilities. Never copy private provider environment files into evidence.

Static provider keys belong only in ignored server `.env` files locally (the existing signaling file is mode 0600), with empty secret placeholders in `.env.example`. Runtime bearers are ephemeral credentials rather than configuration. No private `VITE_*` variable is permitted. The secret check is pattern-based prevention, not a complete secret-detection guarantee.
