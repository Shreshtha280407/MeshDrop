## Lifecycle and memory audit

The owner streams the selected source through incremental SHA-256 before offering
a strict manifest. Receiver consent prepares OPFS and its IndexedDB checkpoint.
The sender reads one verification block, announces it and fragments it through
the reliable ordered WebRTC channel. The receiver assembles one block, checks its
digest, writes/re-reads/flushes OPFS and commits the ledger transaction before ACK.
Only a valid committed ACK advances sender-confirmed progress.

On interruption the old machine aborts and retained checkpoints survive according
to policy. A new admitted epoch and explicit pairing are required. Reopening
rehashes saved blocks; the exact original source is fully checked and authenticates
the reused proofs. Only missing/invalid blocks travel again. Each complete stored
file is rehashed, and a scoped receipt/ACK handshake precedes verified completion.
Export uses a file-backed File/stream, not aggregation of all received chunks.

Existing hard limits remain: 1–16 safe distinct paths, 64 GiB total, 1 MiB
verification blocks, 65,536 block indices per file, paged resume proofs (32/page),
one source/hash/storage RPC outstanding, 512 KiB send high water and 128 KiB drain
threshold, 2 MiB/4,096-message peer receive queue and 64 queued outgoing controls.
Unknown receiver quota permits at most 64 MiB; 300 MiB offers require the existing
additional storage/export acknowledgement. These limits were read from code.

Whole-source hashing is streaming. `arrayBuffer()` in the production source worker
reads only a bounded `File.slice`; manifest hashing handles metadata only. Final
OPFS hashing is incremental. Export wrappers reference file-backed data. Existing
small fake-storage tests do aggregate their deliberately small fixtures; they are
not the production path or the new large-file architecture.

Payload queues are bounded independently of file size. Metadata is bounded by
the declared file/block limits and can grow with block count. The measurements
below are queue/RPC bounds, not a claim of constant whole-browser RSS: browser,
network, GC, OPFS and operating-system caches have additional memory costs.

## Confirmed defects and corrections

1. A receiver disposed while awaiting manifest hashing could later publish a new
   negotiating offer. A deterministic test failed on the original implementation;
   the post-hash abort check prevents the stale update.
2. A sender cancelled while its receipt ACK was being signed/sent could later
   acquire receipt metadata. The stop regression failed before correction. Abort
   signals now propagate through RoomClient and PeerSession, checked before queue
   work and after actual ECDSA signing. Queued success cannot escape cancellation;
   the signed cancellation notification remains possible. Stop paths clear pending
   receipts, and completion explicitly rechecks committed totals/verified files
   before and after asynchronous receiver receipt persistence.
3. The lifecycle observer handled document `freeze` but omitted document `resume`.
   New desktop and mobile-emulated browser tests both stalled on the old epoch.
   The resume listener and matching cleanup now allow safe recovery, still requiring
   the fresh comparison and explicit saved-transfer resume.

The investigation did not establish that the original app falsely verified corrupt
file bytes. Its existing block/final-hash checks worked; these changes harden stop
boundaries and mechanically assert the completion invariant.

## Deterministic large-file and fault evidence

The generated byte at offset `o` is `(31*o + 17*floor(o/1048576) + 19) % 251`.
Reads generate at most 1 MiB. Whole-file `arrayBuffer()` throws deliberately.
The injected engine adapter stores actual bytes in unique disposable local files;
it does not synthesize successful storage or expected final hashes. Production
framing and transfer/recovery state machines run. Node SHA-256 independently
checks the final file against incremental source hashing and fixed reference
hashes. This is **local file-backed transport/storage simulation**, not OPFS,
hosted authorization or a real WebRTC 1 GiB claim.

The 33 dedicated engine cases cover:

- 0/1/10/25/50/75/95% interruption of a 100 MiB logical file, with fresh epoch,
  rehashed checkpoint, missing-only DATA, equal totals and exact final hashes.
- Three recovery cycles in one transfer, finishing on epoch 4 with no retransmitted
  committed blocks. A lost ACK after committing block 4 reuses all five saved
  blocks rather than counting or writing them twice.
- A held committed ACK: sender progress remains zero, scheduling remains at one
  block, and transport/storage queues stay bounded until the ACK is released.
- Duplicate ACK/finalization/resume controls, rejected duplicate DATA and invalid
  sequence/future-block ACKs. Real SCTP is reliable and ordered; invalid-order DATA
  is deliberate defensive input testing, not a claimed network reordering mode.
- Corrupt middle, final and resumed blocks; separately, on-disk damage after valid
  block commitments. No case produces a verified receipt or successful completion.
- Same-name/same-size changed-source rejection, insufficient capacity, write/worker
  failure, quota exhaustion and exact retry commitment without premature ACK.
- Cancellation before DATA, mid-transfer, while paused, during recovery and during
  receipt signing. Queued work cannot revive success; explicit cancellation purges
  fixture partial storage in accordance with the existing policy.

Four explicit old-epoch control cases (ACK, flow, finalize, resume) leave the new
machine unchanged. Real-signature tests reject aborts before queue work and after
signing without preventing a valid signed cancel. Worker error rejects the pending
RPC and subsequent work. Property cases use five fixed seeds and 256 schedules
each (1,280 schedules), plus byte partition/boundary cases through 65,536 blocks.
The union of committed/missing ranges is exact and disjoint; duplicates/invalid
endpoints are rejected and old room epochs cannot be reused.

## Real local browser evidence

over WebRTC into OPFS, pause/resume, final verification and independently hashed
download. Smaller actual browser cases cover peer loss, dispatched freeze/resume,
fresh comparison, exact missing-only recovery, cancellation during actual receipt
signing and storage-failure UI. These ten cases capture no traces/videos/screenshots.
The initial eight passed with zero retries; both newly added freeze cases failed
before the listener fix and passed afterward with zero retries.

This does not certify a physical mobile OS freeze, long-term background delivery,
public Internet throughput, NAT/TURN traversal or browser 256 MiB/1 GiB transfer.
Existing visibility/offline/mobile regressions remain in the full browser suite.
