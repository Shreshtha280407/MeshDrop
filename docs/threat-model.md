# MeshDrop threat model

Original P0–P8 review: 2026-10-18. Internal adversarial re-audit: 2026-11-13 (Task 15). Neither review is an independent third-party penetration test. Historical phase evidence below remains scoped to its original tests; later local controls do not establish hosted release authorization.

Assets: capabilities, peer identity, room isolation, file bytes, checkpoint integrity, local capacity, diagnostics and addresses. Attackers include unauthenticated callers, leaked-invite holders, malicious approved peers, compromised signaling and stale/replayed clients. Local corruption and eviction are also threats to correctness.

The table preserves the initial P0 roadmap. Later paragraphs and the linked Phase 8 security review describe the implemented controls and current evidence.

P0 review: no upload/authentication backdoor is exposed; shared contracts are independent of framework/runtime code; completion is guarded at the lifecycle boundary. Production requires HTTPS/WSS; local loopback is permitted for development.

P1 adds tested capability admission, owner approval, two-peer isolation, single-use origin/revision/epoch-bound tickets, per-message membership/sequence checks, stale-socket generations, alarm expiry and row cleanup. Actual hibernation eviction verifies restored authorization. All raw capabilities remain outside SQLite and logs. See the [P1 signaling contract](protocol/signaling-p1.md) and [secret handling](security/secrets.md). P2 adds signed, DTLS-bound ephemeral identity handshakes; independently compared pairing fingerprints; authenticated epoch changes; bounded ICE queues; signed ping replay rejection; and temporary TURN credentials. Physical Oppo Chrome direct-path and forced local TURN tests are documented in the [P2 report](reports/phase-2.md). Persistent recovery, hostile-network deployment and the remaining physical OS/browser matrix remain later gates. A matching code proves a shared transcript only after an independent comparison; it does not name a person or protect a compromised browser/application origin.

P3 requires signed confirmation from both peers plus receiver consent before file data. Strict manifests reject traversal, reserved/ambiguous paths, duplicate IDs, case-folded collisions and inconsistent totals. Labels never become OPFS paths: each transfer gets a locally generated storage key, with UUID file entries. Binary type-2 frames enforce negotiated lengths, transfer/file/epoch scope and exact block/fragment ordering; malformed/repeated data fails closed. One 1 MiB block in flight, channel watermarks and a bounded receive queue limit owned buffering. Incremental hashes and OPFS writes run in dedicated workers. ACK follows verified write and flush; confirmed progress follows that ACK. Final completion requires full stored-file SHA-256 readback, file verification and receipt acknowledgement. Corruption, failed commit/finalization, forged ACK, pause/cancel and idempotent terminal events have negative coverage. See the [P3 contract](protocol/transfer-p3.md) and [report](reports/phase-3.md).

In P3 the commit frontier existed only in worker memory and crash-orphan cleanup was pending. P4 superseded those limitations with the reconciliation, locks and retention cleanup described below. Flush remains an API-level commit, not proof against power loss or eviction. A malicious peer can lie about its own storage; signatures and SHA-256 authenticate the cooperative protocol, not remote hardware. OPFS is origin-private rather than encrypted against a compromised local profile/origin. Clear/cancel purges only the selected transfer; user-exported downloads remain outside application cleanup. No server-side file, filename, manifest, digest or receipt logging is introduced. Runtime DOM storage errors are reduced to generic messages to avoid leaking local paths.

P4 supersedes the volatile P3 sink with tested OPFS/IndexedDB reconciliation. ACK eligibility follows written-block readback SHA-256, flush and strict IDB transaction completion. Worker termination in five cross-store windows and actual transaction abort demonstrate conservative recovery. Startup validates the manifest and rehashes ledger-backed blocks, drops missing/changed rows, ignores orphan bytes and rechecks complete-file SHA-256 before export. Exclusive Web Locks prevent a second tab from reopening or deleting an active store; scoped tombstones, retention expiry and orphan collection protect cleanup. Quota errors pause without a false ACK and preserve earlier verified blocks; a bounded retry completes only after storage succeeds. Source reselection requires full SHA-256 rather than name/size alone. See the [P4 storage contract](protocol/storage-p4.md) and [report](reports/phase-4.md).

Local metadata/digests are trusted only within the uncompromised origin/profile threat boundary. A saved record is not returning-peer authentication, a durable room capability or proof of physical disk persistence. P5 binds resume to a fresh admitted epoch, independently confirmed pairing transcript, original manifest and source-checked receiver proofs. Browser eviction, permission denial, clearing site data, unsupported modes and physical power loss remain explicit limits. No provider secrets or connection signing keys enter the new database.

P5 checks local saved bytes against their ledger and then source block SHA-256 under authenticated controls. A forged local digest can pass local rehash but cannot become reused progress when it differs from the source. Old epochs/sequence replays are rejected before dispatch; attempt/page/phase checks prevent distinct signed handshake replays from changing the accepted ledger. Full-file verification and a fresh-epoch receipt remain mandatory, including fully reused and empty files. Reconnect retries are bounded, and expiry requires renewed authorization. The returning human identity depends on the independent comparison; it is not a persisted device key or remote hardware attestation. See the [resume contract](protocol/resume-p5.md).

P6 persists only allowlisted timing, byte-count and category evidence in a separate bounded local IndexedDB. Strict schemas reject unknown metadata, raw errors and mismatched metric labels. Selected-pair extraction drops candidates/IPs/ports; JSON/CSV exports are opt-in and never uploaded. Count, byte and expiry pruning plus explicit deletion limit retention; logical caps exclude database overhead. A diagnostics quota/API failure does not decide file integrity. Reports still contain linkable UUIDs, sizes and timings, and origin/profile compromise remains outside the redaction boundary. Sampling cannot establish ISP throttling or Wi-Fi congestion. See the [diagnostics contract](protocol/diagnostics-p6.md).

P7 adds usable storage probes, quota/consent policy, foreground pause/recovery, local QR handling, gesture-preserving native export and an exact public-shell-only offline cache. It makes no background-delivery or universal iPhone export promise. The [21 October P7 continuation](reports/phase-7.md) records actual iPhone normal/recovery/export evidence; Android and Linux engine tests remain separate from that device coverage.

P8 reviews these boundaries and adds persistent room budgets, lazy schema creation for real rooms, upgraded-room cleanup, server-enforced SDP roles, bounded request/chunk/deadline and client queues, portable Unicode/path/output conflict validation, conservative export MIME, strict production headers and release auditing. Deterministic fuzz/property cases, real third-browser denial, malformed WebRTC frame demos, client flood denial, production CSP/referrer tests and independent collision-export bytes provide local evidence. See the [security review](security-review.md), [privacy model](privacy-model.md) and [Phase 8 report](reports/phase-8.md).

History replacement cleans the application-visible URL and current navigation entry but does not guarantee erasure of Chromium userTypedURL metadata or external browser/sync/clipboard copies. There is no payload logging or analytics SDK. Optional Worker audit output contains only a fixed event, environment, allowlisted operation and numeric status. Hosting/runtime retention, global provider capacity, public TLS behavior and real relay enforcement require their own hosted evidence; the original P9 acceptance work and later reports must be read with their stated limits. A compromised origin/profile and malicious exported files remain explicit limits. Hashes are integrity evidence; they do not independently authorize returning peers.

## Task 15 trust boundaries

The [internal adversarial report](reports/task-15-security-privacy-redteam.md) maps the current attack surfaces and distinguishes reproduced defects from tested controls. The review found and corrected three low-severity issues: unsanitized same-document invitation navigation, raw exception/provider messages displayed as UI errors, and persisted receipts retained without checking their manifest context.

Invitation startup, hash navigation, history restoration and BFCache restoration now scrub the current URL before passing the value to application state. Navigation only prefills the invitation field when no room is active; it never admits a peer or replaces active authority. Browser-managed history, clipboard history and copies outside the application remain outside this control.

Reconciliation rehashes persisted bytes and checks receipt transfer ID, manifest digest, total and exact file metadata before restoring completed state. A mismatched receipt is discarded without deleting verified recoverable bytes. This is context consistency, not independent authentication of a locally stored receipt: its original signed transport envelope is not retained. An attacker controlling the entire origin/profile can replace bytes and all local expected metadata together. Fresh network recovery still requires exact-source validation, admission and bilateral pairing; a local record cannot supply any of those authorities.

Task 12 transfer invariants and Task 14 isolation, queue and reconnect protections remain required. Task 15 adds 2,000 seeded schedules using real ECDSA signatures and actual incoming validators, plus isolated HTTP/WebSocket, transfer, browser-storage and PWA attacks. Controlled transport seams do not constitute external network, physical disk, native Safari or hosted penetration-test evidence. Browser cache tests inspect the application's caches; they cannot prove erasure from operating-system or provider caches.

Task10D remains **SKIPPED**, Task11B remains **SKIPPED**, Task13 remains **PARTIAL**, and Task14's verified starting result remains **PASS**. Production approval is false. This review supplies no publication, acceptance, independent reviewer or independent witness authority.
